# Finanzas — Backend

API REST en Node.js + Express + Prisma + PostgreSQL. Fase 1: autenticación y onboarding. Fase 2: gastos personales. Fase 3: settings del hogar (miembros, permisos, conceptos recurrentes, split). Fase 4: panel del hogar (gastos recurrentes por período + gastos variables puntuales, con split por contexto y reparto personalizable por gasto). Fase 5: motor de cortes (liquidación por lotes; desde 2026-11-24 reemplazado por **cuadres abiertos**, ver más abajo). Fase 6: endpoints de agregación para el dashboard. Fase 7 (en curso): reestructuración completa del panel personal — Etapa 1 (catálogos, gastos/ingresos fijos-o-esporádicos con estado pagado/pendiente), Etapa 2 (Disponible + ciclo personal, resumen movido a los módulos de dominio en vez de un módulo `dashboard` aparte) y Etapa 3 (Ahorros con ciclos y evaluación automática — ver `Modulo_Panel_Personal_Ajustes.md`).

## Setup

1. `npm install`
2. Copiar `.env.example` a `.env` y completar `DATABASE_URL` y `JWT_SECRET` (usar un valor largo y aleatorio, por ejemplo `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`)
3. `npm run prisma:migrate` — aplica las migraciones contra la base de datos configurada
4. `npm run dev` — levanta el servidor con recarga automática en `http://localhost:3000`

**Al desplegar esta versión sobre una base existente:** `npx prisma migrate deploy` y después `npm run recalcular-historiales` (sin argumentos solo muestra qué haría; con `-- --aplicar` lo hace). Ver "Estabilización post-Fase 7 Etapa 5" en Notas de diseño.

## Despliegue en Vercel

Proyecto de Vercel con carpeta raíz `backend`, preset "Other" (`framework: null` en `vercel.json`), región `iad1`. `api/index.js` exporta la app de Express (`src/app.js`) como función serverless y `vercel.json` reenvía todas las rutas a esa función; `src/server.js` (con `app.listen`) queda solo para correr local. `postinstall` corre `prisma generate`. Las migraciones **no** corren en el build — se aplican a mano: pruebas con `npx prisma migrate deploy` (`.env`) y producción con `npm run migrar-produccion` (solo el estado) o `npm run migrar-produccion -- --aplicar`, que lee `.env.produccion` (ignorado por git; `DATABASE_URL` y `DIRECT_URL` de Supabase), no imprime las direcciones, y después de migrar activa RLS en todas las tablas y quita los permisos de `anon`/`authenticated` (la app entra como `postgres`, que se salta RLS). Todas las respuestas de la API llevan `Cache-Control: no-store`.

Dos proyectos: `finanzas-backend-pruebas` (rama `despliegue-vercel`, base en la VPS) y `finanzas-backend` (producción, rama `master`, base en Supabase); cada uno ignora los commits de la otra rama.

Variables de entorno: `DATABASE_URL` (pruebas: la VPS con `connection_limit=3&pool_timeout=20`; producción: el pooler de Supabase en modo transacción, puerto 6543, con `?pgbouncer=true&connection_limit=1`), `DIRECT_URL` (solo para migrar; en producción el pooler de sesión, puerto 5432; si falta se usa `DATABASE_URL`, ver `src/config/prisma.js`), `JWT_SECRET`, `NODE_ENV=production` (activa la cookie `secure`), `APP_TZ=America/Bogota` y `FRONTEND_URL` (orígenes a los que CORS acepta credenciales; en el uso normal no hace falta porque el frontend llega por rewrite, mismo origen).

Dentro de una transacción interactiva toda lectura debe usar `tx`, no el cliente global: con pocas conexiones por instancia, la transacción retiene una y la consulta global puede quedarse esperando hasta el timeout (por eso `obtenerOrigenesDetalladosPorLote` en `src/utils/cuadreItemOrigen.js` recibe el cliente).

## Endpoints (Fase 1)

### Auth (`/api/auth`)
- `POST /register` — `{ nombre, usuario, password }` → crea el usuario y setea la cookie de sesión
- `POST /login` — `{ usuario, password }`
- `POST /logout`
- `GET /me` — requiere sesión activa
- `POST /cambiar-password` — `{ actual, nueva }` (sesión activa). Contraseña actual errada → 400 (no 401, que en la app significa "sesión terminada"); usa los mismos límites del login. Cierra las demás sesiones y le da a esta un token nuevo.
- `POST /cerrar-otras-sesiones` — (sesión activa) cierra la sesión en todos los demás dispositivos; esta sigue.
- **Códigos de recuperación** (`modules/auth/recuperacion.service.js`, tabla `CodigoRecuperacion`): `GET /codigos-recuperacion` (sesión) → `{ total, disponibles, creadosEn }`; `POST /codigos-recuperacion` `{ password }` (sesión; contraseña errada → 400, con el límite del login) → `{ codigos }`: 8 nuevos XXXX-XXXX (alfabeto sin 0/O/1/I), guardados con bcrypt (costo 10) y mostrados solo esta vez; borra los anteriores. `POST /recuperar` `{ usuario, codigo, nueva }` (sin sesión; el código se acepta en minúsculas, con o sin guion o espacios) → gasta el código con un `updateMany` condicional, cambia la contraseña, sube `sesionVersion` (cierra todas las sesiones), deja la cookie de esta y una notificación `seguridad`. Error genérico 400 (no delata si el usuario existe); 5 códigos errados para un usuario desde una conexión → 15 min, 10 errados por conexión en una hora → 1 h (429).

La sesión se maneja con una cookie httpOnly, `secure` en producción y `sameSite: lax` (`finanzas_session`), firmada con JWT HS256 (`algorithms` fijado al verificar), con vigencia de ~1 año. El token lleva `v` = `Usuario.sesionVersion`; `requireAuth` lo compara con la base en cada petición, así que subir la versión (cambio de contraseña o "cerrar las demás") invalida los demás tokens al instante. Los tokens de antes (sin `v`) cuentan como versión 0. Si `JWT_SECRET` tiene menos de 32 caracteres, el arranque deja un aviso en el log.

**Límites de intentos** (`src/utils/limiteIntentos.js`, tabla `IntentoAcceso`, por IP con `x-real-ip` / `x-forwarded-for`): 5 contraseñas erradas seguidas de un usuario desde una misma conexión la bloquean 15 min **solo para esa conexión** (nadie puede bloquearte la cuenta desde otra); 30 erradas en 15 min desde una conexión a cualquier usuario la bloquean 15 min; registro: 10 por conexión por hora; `POST /api/hogares/join`: 10 códigos errados por conexión por hora. Responden 429. Los contadores viejos se borran al iniciar sesión. Las columnas viejas `Usuario.intentosFallidos` / `bloqueadoHasta` se quitaron (`20261206130000_quitar_bloqueo_viejo`).

### Hogares (`/api/hogares`) — requieren sesión activa
- `POST /` — `{ nombre }` → crea el hogar, el creador queda como admin con todos los permisos. Falla si el usuario ya pertenece a un hogar. (El hogar ya no tiene frecuencia de corte ni puntos de corte: cada cuenta fija tiene su propio calendario y los cuadres se hacen cuando el hogar decide.)
- `GET /actual` — `{ hogar }` del usuario autenticado
- `PATCH /` — `{ nombre? }`. Requiere admin o `puedeEditarGastos`.
- `POST /invitaciones` — genera un código de invitación de un solo uso (vigencia 7 días). Requiere ser admin o tener `puedeInvitar`.
- `POST /join` — `{ codigo }` → une al usuario autenticado al hogar de esa invitación. Falla si el usuario ya tiene hogar, o si el código es inválido/usado/expirado.
- `GET /miembros` — lista los miembros del hogar con sus permisos
- `PATCH /miembros/:id/permisos` — `{ puedeEditarGastos?, puedeInvitar? }`. Solo admin.
- `POST /transferir-admin` — `{ nuevoAdminId }`. Solo admin; mueve el rol a otro miembro del hogar y registra el cambio en `log_transferencia_admin`.
- `POST /salir` — salir del hogar (el admin, solo si es el último o tras transferir la administración: 409). `DELETE /miembros/:id` — el admin quita a otro miembro (403 si no es admin). Ambos (`salirHogar.service.js`) exigen que la persona no tenga nada del hogar sin cuadrar —gastos variables o cuotas de compras y préstamos de cualquier fecha que pagó o con reparto suyo, y cuotas de cuentas fijas pagadas— ni haya un cuadre abierto (409 con el motivo). Al salir: `hogarId` null y sin permisos, el split vigente (general y de gastos variables) se recalcula desde hoy entre los que quedan en la misma proporción, deja de ser responsable de cuentas fijas, sus invitaciones sin usar se anulan y queda en la actividad ("salió del hogar" / "quitó a X del hogar", que también le llega a quien quitaron). Lo ya cuadrado sigue en el historial con su nombre; su panel personal no cambia.

### Cuentas fijas del hogar (`/api/conceptos-recurrentes`) — requieren sesión activa
Modelo `ConceptoRecurrentePareja` (el nombre del modelo y de la ruta se conservaron; en la app se llaman "cuentas fijas").
- `GET /` — lista las cuentas del hogar con su `responsable`
- `POST /` — `{ nombre, tipoMonto: "fijo" | "variable", montoDefault?, responsableUsuarioId?, frecuencia: "mensual" | "quincenal", diaMes?, diaMes2?, fechaInicio }`. `montoDefault` es obligatorio si `tipoMonto` es `fijo`. Mensual usa `diaMes` (null = último día del mes); quincenal usa `diaMes` (default 15) y `diaMes2` (null = último día), con `diaMes < diaMes2`. Requiere admin o `puedeEditarGastos`.
- `PATCH /:id` — cualquiera de los campos anteriores más `activo`. Las cuotas **por pagar** siguen a la configuración nueva: si cambió el calendario (frecuencia, días o fecha de inicio) se borran y se regeneran solas con las fechas nuevas; si no, se les actualiza el monto. Las ya pagadas no se tocan. Desactivar borra las cuotas futuras sin pagar (las vencidas siguen, son una obligación real). Requiere admin o `puedeEditarGastos`.
- `DELETE /:id` — falla con 409 si la cuenta ya tiene alguna cuota pagada (usa `PATCH { activo: false }`). Requiere admin o `puedeEditarGastos`.

**Pago automático (2026-12-09):** `POST`/`PATCH` aceptan `pagoAutomatico` y `metodoPagoAutomaticoId`. Solo para cuentas de monto `fijo` con responsable (400 si no); el método es privado del responsable: solo él lo elige (400 si lo manda otro) y solo él lo recibe en `GET` (el resto, `null`). Si cambia el responsable el método se borra; si otro miembro edita la cuenta sin mandar el campo, se conserva. `pagoAutomaticoDesde` = `fechaInicio` al crear una cuenta automática, o hoy al activarla en una que ya existe (lo vencido antes sigue pendiente). `asegurarCuotasHogar` termina con `pagarCuotasAutomaticas`: cada cuota con fecha ≤ hoy y ≥ `pagoAutomaticoDesde` queda `pagado` por el responsable con `fechaPago` = su fecha, el método configurado, el split `general` de esa fecha y su movimiento de caja (`sincronizarPagoCuota`), marcada `pagoAutomatico: true` y con una entrada en la actividad del hogar (sin notificar). Cada cuota se toma con un `updateMany` condicional (`estado: por_pagar`), así consultas simultáneas no la pagan dos veces. `seVaAPagarSola(concepto, cuota)` (`utils/cuentasFijas.js`) dice si una cuota se pagará sola: esas no salen en `/api/avisos`, y `GET /api/cuentas-hogar` la devuelve como `seVaAPagarSola`. Además de las pantallas del hogar, los pagos automáticos se generan al consultar el panel personal (`asegurarInstanciasFijasPersonales` y la lista de gastos personales), para que el movimiento le aparezca al responsable. Migración aditiva `20261209120000_cuentas_fijas_automaticas`.

**Un período ya pagado no se vuelve a cobrar:** si cambia el calendario de una cuenta (ej. del día 30 al 5), `asegurarCuotasHogar` no genera cuota en un mes (o quincena) que ya tiene una cuota pagada (`periodoDeCuota`); "Mis próximos meses" usa la misma regla.

**Calendario** (`src/utils/cuentasFijas.js#fechasDeCuenta`): por cada mes desde `fechaInicio`, el día configurado; un día mayor que el largo del mes cae en su último día (30 en febrero → 28/29). Las cuotas (`GastoRecurrenteInstancia`, una por cuenta + fecha, `@@unique([conceptoId, fecha])`) se generan perezosamente con `asegurarCuotasHogar` — todas las de su calendario hasta hoy más la próxima — en una sola query `createMany({ skipDuplicates })`. No hay cron: se llama al consultar cuentas, saldo y cuadres.

### Split de porcentaje (`/api/split-porcentaje`) — requieren sesión activa
- `GET /?contexto=general|gastos_variables` — split vigente para ese contexto (el más reciente con `periodoInicio` ≤ hoy). `contexto` es opcional, default `general`.
- `PUT /?contexto=general|gastos_variables` — `{ splits: [{ usuarioId, porcentaje }] }` → los porcentajes deben sumar 100% entre todos los miembros del hogar (soporta N miembros, no solo 2). Cada actualización crea un nuevo período con fecha de hoy para ese contexto, preservando el historial. Requiere admin o `puedeEditarGastos`.

El split que se aplica a un gasto es el vigente **en la fecha del gasto** (`obtenerSplitVigente(hogarId, contexto, client, fecha)`), no el de hoy; si el gasto es anterior a cualquier split configurado, cae al primero que exista.

Hay dos contextos independientes: `general` (lo usan las cuentas fijas) y `gastos_variables` (default para gastos variables puntuales, ver más abajo). Son splits separados a propósito — configurar uno no toca el otro.

### Cuotas de las cuentas fijas (`/api/cuentas-hogar`) — requieren sesión activa
Una cuota nace `por_pagar` (monto = el de la cuenta si es fija, `null` si es variable, sin pagador) y **solo cuenta para el saldo y los cuadres cuando alguien la marca como pagada** — lo que nadie ha pagado no genera deuda entre los miembros.
- `GET /` — `{ porPagar, proximas, pagadasSinCuadrar }`. `porPagar`: cuotas con fecha ≤ hoy sin pagar (`atrasada: true` si su día ya pasó). `proximas`: la siguiente cuota sin pagar de cada cuenta. `pagadasSinCuadrar`: estado `pagado` o `en_cuadre`.
- `POST /:id/pagar` — `{ monto?, pagoUsuarioId?, fechaPago?, metodoPagoId? }` (`metodoPagoId` solo si quien pagó es el usuario actual y es uno de sus métodos; es privado: el resto del hogar lo recibe en `null`). `monto` es obligatorio si la cuenta es de monto variable; `pagoUsuarioId` por defecto es el responsable de la cuenta. Calcula el reparto con el split `general` vigente en la fecha de la cuota. Se puede pagar una cuota futura: entra al saldo cuando llega su fecha. Requiere admin o `puedeEditarGastos`.
- `POST /:id/deshacer-pago` — vuelve a `por_pagar` y borra el reparto. Falla con 409 si la cuota está en el borrador de un cuadre o ya se cuadró. En una cuenta automática, si la cuota ya llegó a su fecha queda `sinPagoAutomatico` (ej. el cobro falló): no se vuelve a pagar sola y sale en los avisos; se paga con "Lo pagué".

### Gastos variables puntuales (`/api/gastos-variables`) — requieren sesión activa
Un gasto variable (mercado, una compra) nace `pagado`: siempre se registra con quién pagó, así que entra al saldo de una vez. `fecha` es el día del gasto.
- `GET /` — lista los gastos del hogar, más recientes primero
- `POST /` — `{ item, valorTotal, pagoUsuarioId, fecha, repartos? }`. Sin `repartos` usa el split vigente en `fecha`: Si no se pasa `repartos`: usa el split del contexto `gastos_variables` si está configurado, y si no, cae automáticamente al split `general`. Si se pasa `repartos` explícito (reparto personalizado para ESE gasto puntual), debe sumar exactamente `valorTotal` y cada `usuarioId` debe pertenecer al hogar — no afecta ningún split guardado, solo aplica a ese gasto. Requiere admin o `puedeEditarGastos`.
- `PATCH /:id` — igual que crear, todos los campos opcionales; cambiar `valorTotal`, `fecha` o pasar `repartos` recalcula el reparto de ese gasto, cambiar solo `pagoUsuarioId` no lo toca. Solo mientras esté `pagado` (no `en_cuadre` ni `cuadrado`).
- `DELETE /:id` — solo si sigue `pagado` (todavía no está en un cuadre).

### Cuadres de cuentas (`/api/cuadres`) — requieren sesión activa
Reemplazan al motor de cortes por fechas nominales (2026-11-24). **No hay fechas de corte:** el hogar cuadra cuando quiere y el cuadre junta todo lo **pagado y sin cuadrar con fecha ≤ hoy** — cuotas de cuentas fijas marcadas como pagadas y gastos variables — sin importar qué tan atrás esté. Ciclo de cada gasto (`EstadoGastoHogar`): `por_pagar` → `pagado` → `en_cuadre` → `cuadrado`.
- `GET /saldo` — saldo en vivo: `{ totalSinCuadrar, cantidadSinCuadrar, balances: [{ usuario, balance }] }` con todo lo pagado y sin cuadrar con fecha ≤ hoy (positivo = le deben).
- `GET /actual` — el borrador abierto **refrescado** (`refrescarBorrador`): agrega preseleccionado lo pagado nuevo, sincroniza montos con el origen y quita ítems cuyo origen ya no está pagado. Los desmarcados en ese borrador siguen desmarcados. `null` si no hay borrador.
- `POST /` — inicia un borrador (o devuelve el abierto, refrescado). Si no hay nada pagado sin cuadrar responde `{ cuadre: null, motivo }`. Máximo un borrador por hogar. Requiere admin o `puedeEditarGastos`.
- `PATCH /:id/items/:itemId` — `{ incluido }`. Desmarcar devuelve el origen a `pagado`: queda para el siguiente cuadre aunque su fecha ya haya pasado.
- `DELETE /:id` — descarta el borrador; todo vuelve a `pagado`.
- `POST /:id/confirmar` — cierra el cuadre con lo marcado (sin refrescar: se confirma exactamente lo revisado; falla con 409 si algo cambió mientras tanto). Calcula el balance por miembro (`cuadre_balance_miembro`), pasa los ítems a `cuadrado`, borra los ítems desmarcados del cuadre (siguen `pagado`) y guarda `fecha` = día del cuadre.
- `GET /` — historial de cuadres cerrados, más reciente primero, con sus ítems. `GET /:id` — detalle.
- `GET /resumen` — informe del hogar por **mes calendario** según la fecha de cada gasto pagado (no según cuándo se cuadró), últimos 6 meses con movimientos: `serieMensual [{ periodo, totalCuentasFijas, totalVariables }]`, `pagadoPorMiembro`, `ultimoCuadre`.

El balance se guarda **por miembro** (positivo = le deben, negativo = debe): con 2 personas se lee "Daniela le debe $X a Mateo", pero el modelo soporta N miembros.

**Integración con el panel personal (caja vs. consumo, 2026-11-25):** el panel personal separa dos vistas.
- **Caja** (movimientos y Disponible: la plata que de verdad sale y entra). Al pagar un gasto del hogar (`Lo pagué` en una cuota, un gasto variable, o una cuota de compra del hogar), en los movimientos de quien pagó aparece el **100 %** con su método y fecha de pago (`GastoPersonal` origen `pago_hogar`, enlazado por `pagoCuotaHogarId`/`pagoGastoHogarId` con `onDelete: Cascade`; lo mantiene `src/utils/movimientosHogar.js` en cada pagar/editar/deshacer). Al confirmar un cuadre (`POST /:id/confirmar` con `{ metodoPagoId? }`), cada miembro con neto ≠ 0 recibe su **liquidación**: un reintegro (`IngresoPersonal` origen `liquidacion_hogar`) o un pago (`GastoPersonal` origen `liquidacion_hogar`); quien confirma puede indicar en privado el método del suyo. Estos movimientos no se editan ni borran desde el panel personal (409), salvo el **método**: `PATCH /api/gastos-personales/:id/metodo` y `PATCH /api/ingresos-personales/:id/metodo` (`{ metodoPagoId | null }`, uno de los métodos del propio usuario) permiten a cada quien definirlo después — por ejemplo el miembro que no confirmó el cuadre, o a quien otro le marcó un pago. En un pago del hogar el método también se guarda en el gasto del hogar.
- **Consumo** (informes, Límites, Ahorros, Neto del ciclo: lo que cada uno gastó). `src/utils/consumo.js#gastosDeConsumo` suma los gastos personales propios (sin los orígenes `pago_hogar`, `liquidacion_hogar`, `pago_tarjeta`) más la **parte** del usuario (su reparto) de cada gasto del hogar ya pagado, en la fecha del gasto, como obligatorio y con categoría "Hogar". `ingresosReales` excluye los reintegros. Los gastos "Hogar · mes" del modelo anterior (origen `cuadre_hogar`) ya no se generan (la migración `20261125180000_caja_hogar_y_tarjetas` los borró) y `npm run sincronizar-movimientos-hogar -- --aplicar` crea los movimientos de pagos del hogar hechos antes.

Lo que sigue describe el modelo anterior, que ya no aplica: Al confirmar, por cada miembro se suma su **reparto** de los ítems (su parte real, sin importar quién pagó) **agrupado por mes de la fecha de cada gasto**, y se crea un `GastoPersonal` por miembro y mes (`origen: cuadre_hogar`, `origenCuadreId`, `esObligatorio: true`, `estado: pagado`, `@@unique([origenCuadreId, usuarioId, fecha])`), fechado el último día de ese mes, o el día del cuadre si es el mes en curso. Así un cuadre que abarca septiembre y octubre deja un gasto en cada mes y los informes personales mensuales siguen cuadrando. Después se llama `evaluarPeriodoSiCorresponde` (Ahorros) por cada gasto generado. Eliminar uno de estos gastos está bloqueado con 409.

### Ciclo personal (`/api/ciclo-personal`) — requiere sesión activa
- `GET /` — `Usuario.frecuenciaCicloPersonal` vigente (default `mensual`).
- `PATCH /` — `{ frecuenciaCicloPersonal }`. A diferencia de la frecuencia de corte del hogar, acá no hay puntos de corte que regenerar — el período se recalcula puramente por calendario cada vez que hace falta (`src/utils/cicloPersonal.js`), así que cambiarla no dispara ningún efecto secundario en el schema.

### Resumen personal (`GET /api/resumen-personal?ciclo=0`) — requiere sesión activa
Reemplaza el antiguo `GET /api/dashboard/personal` de Fase 6. **Navegación por ciclos (Etapa 6):** `ciclo` es un índice relativo (0 = el actual, -1 = el anterior… hasta -24; futuro o más atrás → 400), que `calcularPeriodoPorIndice` traduce a fechas con `Usuario.frecuenciaCicloPersonal`; lo aceptan también `GET /api/limites-personales/resumen` y `GET /api/ahorros-personales/resumen`, y los tres devuelven `ciclo: { indice, inicio, fin }` (el resumen además `frecuencia`). En un ciclo pasado: `disponible` y `deudaTarjetas` al cierre (movimientos con fecha ≤ fin), `neto` de ese ciclo contra el anterior a él, `compromisosPendientes` de ese ciclo que siguen pendientes, `serieMensual` hasta el mes del fin del ciclo; `porCategoria` es siempre solo el ciclo consultado. Devuelve:
- `disponible` — Σ ingresos `recibido` − Σ gastos `pagado`, **histórico completo** (no por período; es "cuánto tengo ahora").
- `neto` — `{ actual, anterior, variacionPct, periodoActualInicio, periodoActualFin }`: ingresos − gastos dentro del ciclo actual vs. el anterior, usando `Usuario.frecuenciaCicloPersonal` (reemplaza la comparación "mes actual vs. mes anterior" de Fase 6, que usaba mes calendario fijo).
- `compromisosPendientes` — gastos + ingresos en `pendiente`, combinados y ordenados por fecha ascendente.
- `serieMensual`/`porCategoria` — igual que en Fase 6 (hasta 6 meses con datos reales, categoría vía relación).

### Gastos personales (`/api/gastos-personales`) — requieren sesión activa
- `GET /` — antes de listar, **asegura** (`asegurarInstanciasFijas`) que existan las ocurrencias de cada `GastoFijoConfig` activo entre su `fechaInicio` y hoy, generándolas directamente como filas reales de `GastoPersonal` (no hay tabla de "instancia" separada ni evento de corte) — en estado `pagado` si el concepto es de cobro automático, `pendiente` si es manual. Devuelve todo (fijos ya generados + esporádicos) ordenado por fecha descendente.
- `POST /` — `{ monto, fecha, descripcion?, estado?, esObligatorio?, metodoPagoId?, categoriaId? }` → gasto esporádico (sin `origenConfigId`); `estado` default `pagado`.
- `PATCH /:id` — edita cualquier campo, incluido `estado` (para marcar `pendiente → pagado` una vez que un gasto de cobro manual efectivamente sale de la cuenta).
- `DELETE /:id` — solo gastos esporádicos; falla con 409 si el gasto viene de un `GastoFijoConfig` (`origenConfigId` no nulo) — si se permitiera, la próxima vez que se liste volvería a generarse esa misma fecha, porque el config seguiría activo. Para dejar de generarlas, desactiva el concepto fijo (`PATCH /api/gastos-fijos-config/:id { activo: false }`).

### Ingresos personales (`/api/ingresos-personales`) — requieren sesión activa
Mismo patrón exacto que gastos personales, sin `esObligatorio`: `GET /` asegura instancias de `IngresoFijoConfig` (`recibido` si es automático, `pendiente` si es manual), `POST /` crea esporádicos, `PATCH /:id` edita/marca `recibido`, `DELETE /:id` bloqueado para ingresos de origen fijo.

### Gastos fijos (`/api/gastos-fijos-config`) e ingresos fijos (`/api/ingresos-fijos-config`) — requieren sesión activa
- `GET /`, `POST /`, `PATCH /:id`, `DELETE /:id` — CRUD del concepto recurrente (`nombre, monto, frecuencia, fechaInicio, modoCobro/modo, categoriaId?`; gastos además `esObligatorio`, `metodoPagoIdDefault?`). `fechaInicio` ancla la primera ocurrencia — las siguientes se calculan sumando el paso de la frecuencia (7/15 días o 1 mes calendario) desde ahí, sin "puntos de corte" compartidos como en el hogar: cada concepto fijo personal tiene su propio calendario independiente. `DELETE` falla con 409 si el concepto ya generó ocurrencias (usa `PATCH { activo: false }` para desactivarlo sin perder el historial).

### Compras a cuotas (entrega B) — requieren sesión activa
Una compra a cuotas crea **de una vez** todas sus cuotas como gastos normales con `compraId` + `numeroCuota` (`@@unique([compraId, numeroCuota])`). Monto de cada cuota = total / N redondeado hacia abajo, el residuo en la última (`src/utils/cuotas.js#dividirEnCuotas`); fechas una por mes desde la primera, mismo día (31 en febrero → su último día). `modoCobro`: `automatico` (tarjeta, débito automático) o `manual` (crédito de almacén).
- **Personales** (`/api/compras-cuotas-personales`, modelo `CompraCuotasPersonal`, cuotas en `GastoPersonal`): `GET /`, `POST /` (`{ descripcion, montoTotal, numeroCuotas, fechaPrimeraCuota, modoCobro, metodoPagoId?, categoriaId?, esObligatorio? }`), `PATCH /:id` (mismos campos, opcionales: descripción/categoría/método/obligatorio se aplican a todas las cuotas; cambiar monto, número de cuotas, primera cuota o modo recalcula todas las cuotas — 409 si la compra es manual y ya hay cuotas marcadas pagadas), `DELETE /:id` (409 si alguna cuota está pagada). Automáticas: cada cuota se crea `pagado` si su fecha ya pasó y `pendiente` si no, y pasa sola a `pagado` cuando llega su fecha (`pagarCuotasAutomaticasVencidas`, dentro de `asegurarGastosFijos`, mismo patrón perezoso que los fijos). Una cuota suelta no se puede eliminar (409). `GET /sugerir-primera-cuota?fechaCompra&metodoPagoId` sugiere la primera fecha (`sugerirFechaPrimeraCuota`): tarjeta con corte y pago → el día de pago siguiente al corte que toma la compra (comprar el mismo día del corte cuenta en ese corte); con solo día de pago → ese día del mes siguiente; sin datos → un mes después.
- **Del hogar** (`/api/compras-cuotas-hogar`, modelo `CompraCuotasHogar`, cuotas en `GastoVariablePareja`): `GET /`, `POST /` (`{ item, montoTotal, numeroCuotas, fechaCompra, fechaPrimeraCuota, modoCobro, pagoUsuarioId, metodoPagoId?, repartos? }`), `PATCH /:id` (mismos campos, opcionales: el ítem se cambia siempre y el método solo lo pone el pagador; cambiar monto, número de cuotas, fechas, modo, quién paga o el reparto recalcula todas las cuotas conservando el reparto que ya tenía salvo que se mande uno nuevo — 409 si alguna cuota ya está en un cuadre o, si es manual, ya se marcó pagada; cambiar quién paga quita el método del pagador anterior), `DELETE /:id` (409 si alguna cuota ya está en un cuadre). Automáticas: todas nacen `pagado` y entran al saldo/cuadre solas cuando llega su fecha (saldo y cuadres solo toman fecha ≤ hoy). Manuales: nacen `por_pagar`; `POST /api/gastos-variables/:id/pagar` y `/:id/deshacer-pago`. El reparto de todas las cuotas usa el split vigente el día de la compra, o el reparto personalizado escalado a cada cuota. **Privacidad:** el método de pago es del pagador; solo él puede asociarlo (400 si no) y el `GET` se lo oculta al resto del hogar. Una cuota del hogar no se edita ni elimina suelta (409).
- **Adelantar en el cuadre:** el borrador también trae lo pagado con fecha futura (cuotas automáticas, cuentas pagadas antes de tiempo), **desmarcado**; marcarlo lo cuadra de una vez. En el gasto personal del cuadre, un mes futuro queda fechado en la última cuota de ese mes, así cae en el mes al que pertenece.

### Intereses en compras a cuotas (entrega C1)
La tasa vive en el **método de pago**: una tarjeta de crédito o un crédito de almacén guarda `tasaMensual` y `sistemaInteres`, y las compras a cuotas con ese método los **heredan** (`src/utils/cuotas.js#interesDeCompra`). Una compra puede traer los suyos (`tasaMensual: 0` = promoción sin interés, u otra tasa); sin método o sin tasa en el método, sin interés. En el hogar la tasa sale del método del pagador. Cada compra guarda la tasa con que se calculó, así que cambiar la de la tarjeta solo afecta compras nuevas. Las compras a cuotas (personales y del hogar) aceptan `tasaMensual` (% mensual, 0 = sin interés, máx. 10) y `sistemaInteres`: `capital_fijo` (abono fijo a capital + interés sobre el saldo que falta; las cuotas bajan — por defecto) o `cuota_fija` (francés). `src/utils/cuotas.js#calcularCuotas` devuelve `{ monto, capital, interes }` por cuota en COP enteros (el capital suma exacto el total); cada cuota (`GastoPersonal` / `GastoVariablePareja`, y el movimiento de caja `pago_hogar` de una cuota del hogar) guarda `capital` e `interes`. En el hogar el reparto va sobre el valor total de la cuota, interés incluido. Cambiar la tasa o el sistema al editar una compra recalcula todas las cuotas (mismas reglas que los demás cambios estructurales).

### Informe por método de pago (`GET /api/informe-metodos/:metodoId?mes=YYYY-MM`) — requiere sesión activa
Privado (404 si el método no es del usuario). `mes`: gastos pagados y ingresos recibidos con ese método en el mes, `totalGastos`, `totalIngresos`, `interesesMes`. Si es tarjeta de crédito, `tarjeta`: `deuda`, `comprasVivas` (compras a cuotas personales y del hogar cargadas a ella con cuotas aún por venir: cobradas/total, saldo e interés pendiente, próxima cuota, fin), `pagos` (pagos registrados a la tarjeta), `proximosPagos` (mes actual + 6, capital/interés/total de lo que se cargará) e `interesesTotales` (de las cuotas ya cobradas).

### Extractos de tarjeta (`/api/extractos-tarjeta`, entrega C2) — requiere sesión activa
Solo tarjetas de crédito con `diaCorte` (400 si no; 404 si la tarjeta no es del usuario). Ciclos en `src/utils/ciclosTarjeta.js`: un extracto con corte C cubre las compras de contado con fecha en (corte anterior, C] y las cuotas (personales o del hogar pagadas con la tarjeta) con fecha en (pago anterior, pago de C] — la fecha de una cuota es el día en que se paga; sin `diaPago`, las cuotas usan el rango de corte. Los pagos del hogar entran al 100 % y no se corrigen desde aquí (409).
- `GET /:metodoId` — últimos 6 cortes (el en curso primero, más los extractos guardados de cortes viejos) con `esperado`, `noCobrado`, `reclamos`, `totalBanco`, `diferencia` (= banco − (esperado − noCobrado) − reclamos no aceptados) y `estado`; además `reclamosPendientes` de la tarjeta.
- `GET /:metodoId/ciclos/:fechaCorte` — detalle: `ciclo`, `lineas` (cargos de la app, con `tipo` compra/cuota/ajuste, `delHogar`, `corregible`), `extracto` con sus `ajustes` y `totales`. La fecha tiene que ser un corte de la tarjeta (o un extracto ya guardado).
- `PUT /:metodoId/ciclos/:fechaCorte` — `{ totalBanco?, notas? }` (crea el extracto si no existe).
- `POST /:metodoId/ciclos/:fechaCorte/ajustes` — `tipo`: `correccion` `{ gastoId, monto }` (cambia el valor del gasto; en una cuota la diferencia con el capital queda como interés; corregir otra vez actualiza la misma corrección), `no_cobrado` `{ gastoId }`, `cargo` `{ concepto: interes|mora|cuota_manejo|seguro|comision|avance|otro, monto, descripcion?, categoriaId? }` (crea un `GastoPersonal` pagado con la tarjeta en la fecha de corte), `no_reconocido` `{ monto, descripcion, fecha? }` (reclamo pendiente, sin gasto).
- `POST /:metodoId/ciclos/:fechaCorte/revisar` — `{ revisado }`: revisado exige `totalBanco` y guarda `totalEsperado`; con el extracto revisado no se agregan ni quitan ajustes (409) hasta reabrirlo.
- `PATCH /ajustes/:id` — `{ estadoReclamo: pendiente|reversado|aceptado }`, también con el extracto revisado: aceptado crea el gasto; volver de aceptado lo borra.
- `DELETE /ajustes/:id` — corrección: devuelve el valor anterior; cargo o reclamo aceptado: borra su gasto.
Un gasto creado por un ajuste no se borra desde `/api/gastos-personales` (409) y una tarjeta con extractos no se elimina (409). `ExtractoAjuste.origen` (`manual`/`ia`) queda listo para la lectura del PDF con IA (C3).

### Mis próximos meses (`GET /api/proyeccion-personal?meses=6`) — requiere sesión activa
Por cada mes (el actual y los siguientes): `hogarCuentasFijas` (mi parte de las cuotas de cuentas fijas: el reparto real si ya se pagó; si no, el monto por mi porcentaje del split vigente; las de monto variable se estiman con su costo mensual promedio — la suma de lo pagado en cada mes, en los últimos 3 meses completos (todas sus cuotas pagadas: 3 meses de una quincenal son 6 pagos; si aún no hay meses completos, los meses con algún pago escalados al mes completo) — repartido entre las cuotas del mes, y marcan `estimado` (`costoMensualPromedio`)), `hogarCuotas` (mi reparto de cuotas de compras del hogar), `fijosPersonales` (proyección de `GastoFijoConfig`, con el monto real de la fila si ya existe), `cuotasPersonales`, `ingresosEsperados` (ingresos fijos proyectados + los sueltos ya registrados en ese mes), `comprometido`, `libre` y `detalle`. Los gastos personales de origen `cuadre_hogar` no se suman aparte (serían la misma plata dos veces). Solo la parte del usuario: privado como el resto del panel personal.

### Avisos y notificaciones (`/api/avisos`, `/api/notificaciones`) — requieren sesión activa (salvo el cron)
- `GET /api/avisos` → `{ personales, hogar, diasAviso }`: cada aviso `{ id, tipo (gasto|cuota_compra|cuota_prestamo|tarjeta|cuenta_hogar), ambito, titulo, monto, fecha, dias, estado (atrasado|hoy|proximo), enlace, responsable?, paraMi }`. Personales: `GastoPersonal` pendientes con fecha ≤ hoy + 3 que se pagan a mano (sin cuotas automáticas ni movimientos `pago_hogar`) y tarjetas con `diaPago` dentro de 3 días, deuda > 0 y sin pago registrado en los últimos 25 días. Hogar: cuotas `por_pagar` de cuentas fijas (le tocan al responsable, o a todos si no hay) y cuotas manuales de compras y préstamos (al pagador). De paso genera las notificaciones.
- Notificaciones: `GET /` (las últimas 60 + `noLeidas`), `GET /resumen` (`noLeidas`; regenera como mucho cada 5 min por usuario), `PATCH /:id` `{ leida }`, `POST /leer-todas`, `POST /dispositivos` `{ token, plataforma? }` y `DELETE /dispositivos` `{ token }` (tokens de Firebase para la APK). `POST /generar` (sin sesión) exige `Authorization: Bearer <CRON_SECRET>`; sin esa variable responde 404.
- `notificar(usuarioId, { tipo, titulo, mensaje, enlace, clave })` (`src/utils/notificaciones.js`) guarda una sola vez por `clave` y llama a `enviarPush` (`src/utils/canalPush.js`), que hoy devuelve false; ahí se conecta Firebase (pasos en el comentario del archivo).

### Actividad del hogar (`GET /api/hogares/actividad?limite=40`) — requiere sesión activa
Lo último que pasó en el hogar, con quién lo hizo (`usuario`), `descripcion`, `monto` y `enlace`. Se escribe con `registrarActividad(usuarioActual, { tipo, descripcion, monto, enlace, avisar })` (`src/utils/actividadHogar.js`, después de guardar; si falla no deshace nada): `avisar: 'otros'` (por defecto) notifica a los demás miembros, `'nadie'` solo lo deja en la actividad y una lista de ids avisa solo a esos. `registrarPago` cubre los "Lo pagué": si quien pagó es otro miembro, lo anota como "registró que X pagó …" y le avisa a esa persona para que elija su cuenta; si no, "pagó …" para los demás. Gastos variables y cuotas guardan `registradoPorId` (cuentas fijas: `pagoRegistradoPorId`) y el movimiento de caja lo hereda (`GastoPersonal.registradoPor` en `GET /api/gastos-personales`).

### Categorías y topes del hogar (`/api/categorias-hogar`, `/api/topes-hogar`, entrega E4) — requieren sesión activa
Verlas: cualquier miembro. Crear, editar o borrar: `puedeEditarGastos` o admin (403).
- **Categorías** (`CategoriaHogar`, nombre único por hogar): `GET /` (con `usos`), `POST /` `{ nombre }` (409 si se repite), `POST /basicas` (crea las que falten de Mercado, Servicios, Arriendo, Salidas, Transporte, Mascotas, Salud y Otros), `PATCH /:id` `{ nombre?, activo? }` (desactivar también desactiva su tope), `DELETE /:id` (solo sin usos; si no, 409: desactívala). `GET /gasto?mes=YYYY-MM` (por defecto el actual) → `{ mes, total, categorias: [{ clave, categoriaId, nombre, monto, porcentaje }] }`, de mayor a menor.
- Se eligen con `categoriaId` (opcional) en gastos variables, compras a cuotas del hogar (sus cuotas la copian; editarla en la compra la cambia en todas, aunque estén cuadradas) y cuentas fijas (todas sus cuotas cuentan en ella). Se valida que sea del hogar y esté activa (o que ya fuera la del registro) con `validarCategoriaHogar`. En un gasto variable, un `PATCH` con solo `categoriaId` se acepta aunque esté en un cuadre o cuadrado (no mueve plata).
- **Qué cuenta** (`src/utils/topesHogar.js`, `gastoPorCategoria`): lo pagado (`pagado`/`en_cuadre`/`cuadrado`) con fecha en el mes y ≤ hoy, sin importar quién pagó: cuotas de cuentas fijas, gastos variables y cuotas de compras por su categoría, cuotas de préstamos del hogar como "Préstamos"; los abonos a capital no. Lo que nadie ha pagado y lo automático con fecha posterior a hoy va en "por pagar".
- **Topes** (`TopeHogar`, mensual por mes calendario, de una categoría o del total con `categoriaId: null`; uno activo por categoría o total, 409): `GET /`, `POST /` `{ categoriaId?, montoMensual }`, `PATCH /:id` `{ montoMensual?, activo? }`, `DELETE /:id` (borra también sus fotos). `GET /resumen` → `{ mes, mesAnterior, topes: [{ id, nombre, categoriaId, montoMensual, gastado, porPagar, restante, porcentaje, estado (dentro|cerca ≥ 80 %|excedido), mesAnterior? { montoTope, gastado, estado } }] }`. El mes anterior se guarda en `TopeHogarMes` la primera vez que se consulta (solo topes creados antes de que terminara), así cambiar el monto no reescribe lo pasado.
- **Avisos:** al quedar en "cerca" o "excedido", cada miembro recibe una notificación `tope_hogar` (clave `tope:<id>:<YYYY-MM>:80|excedido`, una sola vez). Se revisa al consultar el resumen y después de cada `registrarActividad` (`revisarTopesHogar`).

### Exportar (`GET /api/exportar`) — requiere sesión activa
`?formato=xlsx|csv` (por defecto xlsx), `tabla=movimientos|consumo|hogar|cuadres|prestamos|ahorros` (solo CSV; por defecto movimientos), `desde`/`hasta` (YYYY-MM-DD, opcionales; desde > hasta → 400). XLSX: un libro con una hoja por tabla (encabezado fijo, montos con formato de pesos, "Sin datos en este rango" si está vacía); CSV: una tabla separada por `;`, con BOM UTF-8 y CRLF. Las tablas (`src/modules/exportar/exportar.service.js`): **Movimientos** (gastos e ingresos del usuario con categoría, cuenta, estado, origen y valor con signo), **Consumo por mes** (`gastosDeConsumo` por mes y categoría), **Hogar** (cuentas fijas y gastos variables pagados, categoría, quién pagó y la parte de cada miembro; sin cuentas), **Cuadres** (cerrados en el rango, con total y balance por miembro), **Préstamos** (todas las cuotas de los visibles, con tu parte) e **Inversiones y ahorros** (aportes, retiros, valoraciones, metas del hogar y ahorros personales). Nada se guarda en el servidor.

### Ahorros personales en la caja
Cada `AhorroTransaccion` (aporte manual, débito automático al evaluar un período, o retiro: `POST /api/ahorros-personales/:id/transacciones` `{ tipo?: aporte|retiro, monto, fecha?, metodoPagoId? }`) crea su movimiento de caja con `crearCajaAhorro` (`src/utils/movimientosAhorro.js`): aporte = `GastoPersonal` origen `aporte_ahorro`, retiro = `IngresoPersonal` origen `retiro_ahorro`, enlazados por `ahorroTransaccionId` y fuera del consumo y de los ingresos reales. Lo ahorrado es aportes − retiros (`netoAhorro`); un retiro no puede superarlo (400). `DELETE /api/ahorros-personales/:id/transacciones/:transaccionId` quita un movimiento manual (los débitos automáticos no, 409). El resumen trae las `transacciones` de cada meta y el patrimonio suma lo ahorrado (`totalAhorrosDe`). `npm run ahorros-en-caja` (con `-- --aplicar`) crea la caja de transacciones anteriores al cambio.

### Inversiones (`/api/inversiones`) y metas en pareja (`/api/metas-hogar`), entrega D2 — requieren sesión activa
Aportes y retiros son siempre de quien los registra y mueven su caja (`src/utils/movimientosAhorro.js`): aporte = `GastoPersonal` (origen `aporte_inversion` / `aporte_meta_hogar`, fuera del consumo), retiro = `IngresoPersonal` (origen `retiro_inversion` / `retiro_meta_hogar`, fuera de los ingresos reales); se enlazan con `inversionMovId` / `metaHogarMovId` y se borran con el movimiento. No se editan ni borran desde gastos/ingresos personales (409). La cuenta de un movimiento solo la ve quien lo hizo.
- **Inversiones:** `GET /` → `{ personales, hogar, resumen: { valorPersonal, valorHogar, miParteHogar, gananciaPersonal } }` (solo las activas suman valor). Cada una: `aportes`, `retiros`, `valorActual` + `origenValor` (`valoracion`: la última ± movimientos posteriores; `estimado`: con `tasaEA`, interés compuesto por aporte hasta hoy o el vencimiento; `aportes`: lo puesto), `ganancia` (valor + retiros − aportes), `rentabilidadPct`, `valorAlVencer`, y en el hogar `participaciones` y `miParte` (por lo puesto, `participaciones()` en `src/utils/inversiones.js`). `POST /` `{ ambito, nombre, tipo?, entidad?, fechaInicio, tasaEA?, fechaVencimiento?, aporteInicial? { monto, fecha?, metodoPagoId? } }` (hogar: permiso de edición); `PATCH /:id` (nombre, tipo, entidad, tasa, vencimiento, `activa`); `DELETE /:id` solo sin movimientos (409: ciérrala); `POST /:id/movimientos` `{ tipo: aporte|retiro, monto, fecha?, metodoPagoId? }` (cualquier miembro); `DELETE /:id/movimientos/:movId` (solo el propio, 403); `POST /:id/valoraciones` `{ valor, fecha? }` (una por fecha, upsert); `DELETE /:id/valoraciones/:valId`.
- **Metas en pareja:** `GET /` → metas con `ahorrado`, `falta`, `progresoPct`, `cumplida`, `porMiembro`, `miAporte`, `mesesRestantes` y `faltaAlMes` (falta / meses hasta `fechaMeta`). `POST /` `{ nombre, montoMeta, fechaMeta? }`, `PATCH /:id` (incluye `activa`), `DELETE /:id` (sin movimientos) piden permiso de edición; `POST /:id/movimientos` `{ tipo, monto, fecha?, metodoPagoId? }` cualquier miembro (un retiro no puede superar lo ahorrado); `DELETE /:id/movimientos/:movId` solo el propio.
- **Patrimonio:** `GET /api/resumen-personal` (ciclo actual) trae `patrimonio: { total, disponible, inversiones, metasHogar, deudaTarjetas, prestamos }` = disponible + inversiones (mías + mi parte del hogar, `valorInversionesDe`) + mis aportes netos en metas activas (`misAportesEnMetas`) − deuda de tarjetas − préstamos (`deudaPrestamosDe`). En un ciclo pasado es `null`.

### Préstamos (`/api/prestamos`, entrega D1) — requieren sesión activa
Personales (solo su dueño) o del hogar (todos los miembros los ven; crear, pagar, abonar y editar piden `puedeEditarGastos` o admin). Cálculos en `src/utils/prestamos.js` (`tasaMensualDe`: E.A. → mensual con (1+EA)^(1/12)−1; `planPorNumero`; `planPorCuota`: misma cuota y la última menor) sobre `calcularCuotas`.
- `GET /` — `{ personales, hogar, resumen: { deudaPersonal, deudaHogar, miParteHogar, interesesPendientes, ordenSugerido } }`. Cada préstamo trae `saldoCapital` (saldoInicial − capital de cuotas pagadas − abonos), `cuotasPagadas`/`totalCuotas` (incluye `cuotasPrevias`), intereses pagados (con mora) y por pagar, `atrasadas`, `proximaCuota`, `terminaEn`, `miPorcentaje`, `cuotas` y `abonos`. Una cuota del hogar está pagada si no está `por_pagar` y su fecha de pago (o la de la cuota, si es automática) ya llegó. La cuenta (`metodoPagoId`) solo la ve quien paga.
- `POST /` — `{ ambito: personal|hogar, nombre, entidad?, tipo?, montoPrestado + plazoMeses | enCurso + saldoActual + cuotasRestantes + cuotasPagadas?, tasa?, tasaEsAnual?, sistemaInteres? (cuota_fija), seguroMensual?, fechaDesembolso?, fechaPrimeraCuota, modoCobro? (manual), metodoPagoId?, pagoUsuarioId (hogar), categoriaId? (personal), desembolso? { metodoPagoId?, fecha? } }`. Personal: cuotas en `GastoPersonal` (`prestamoId`, obligatorias, `fechaVencimiento`); automático: pagadas en su fecha (también en `pagarCuotasAutomaticasVencidas`). Hogar: cuotas en `GastoVariablePareja` (`prestamoId`) repartidas con el split **general** vigente al desembolso; automático: nacen `pagado`, manual: `por_pagar`. `desembolso` crea un `IngresoPersonal` origen `desembolso_prestamo` (fuera de `ingresosReales`).
- `PATCH /:id` — nombre, entidad, tipo, categoría, cuenta, modo y (hogar) quién paga; se aplican a las cuotas sin pagar. Monto, tasa y plazo no se editan.
- `DELETE /:id` — solo sin cuotas pagadas ni abonos (409).
- `POST /:id/cuotas/:numero/pagar` — `{ fecha?, monto?, metodoPagoId?, pagoUsuarioId? }`: "Lo pagué". `monto` mayor que la cuota guarda la diferencia en `mora` (en el hogar se reparte igual). Personal: `fecha` pasa a ser la de pago. `POST /:id/cuotas/:numero/deshacer-pago` — solo préstamos manuales y cuotas que no entraron a un cuadre.
- `POST /:id/abonos` — `{ monto ≤ saldo, fecha?, modo: reducir_plazo|reducir_cuota, metodoPagoId?, pagoUsuarioId? }`: crea el `PrestamoAbono`, su movimiento (personal: `GastoPersonal` origen `abono_prestamo`, fuera del consumo; hogar: `GastoVariablePareja` con `abonoPrestamoId`, repartido, que entra a los cuadres y no cuenta en el consumo) y recalcula las cuotas sin pagar. `DELETE /:id/abonos/:abonoId` lo quita y recalcula con el mismo modo (no si ya entró a un cuadre).
Las cuotas y abonos no salen en `GET /api/gastos-variables` y no se editan desde gastos personales ni del hogar (409); "Mis próximos meses" los suma como cuotas.

### Tarjetas de crédito: deuda y pago (`POST /api/metodos-pago-personales/:id/pagos`)
Una compra (o cuota, o pago del hogar) con un método `tarjeta_credito` es consumo en su fecha pero **no baja el Disponible**: la plata sale cuando se paga la tarjeta. `POST /:id/pagos` (`{ monto, fecha, metodoPagoId? }` — la cuenta de origen, que no puede ser otra tarjeta de crédito) registra ese pago como `GastoPersonal` origen `pago_tarjeta` con `tarjetaPagadaId`: baja el Disponible y no es consumo. `GET /` devuelve `deuda` en cada tarjeta (cargos pagados con ella − pagos registrados) y `GET /api/resumen-personal` devuelve `deudaTarjetas` total.

### Punto de partida (saldo inicial, deuda inicial y compras en curso)
- `saldoInicial: { monto, fecha }` (opcional) en `POST /api/metodos-pago-personales`, y `PUT /:id/saldo-inicial` (`{ monto ≥ 0, fecha }`, 0 lo quita) para cambiarlo. En una cuenta crea un `IngresoPersonal` origen `saldo_inicial` ("Saldo inicial de X", recibido): sube el Disponible sin ser ingreso real. En una tarjeta de crédito crea un `GastoPersonal` origen `saldo_inicial` ("Deuda inicial de X", pagado, con la tarjeta): sube su deuda sin ser consumo ni bajar el Disponible. Uno por método (guardar reemplaza). Crédito de almacén con monto > 0 → 400 (lo que se debe ahí va como compra en curso). Cambiar el tipo de cuenta ↔ tarjeta vuelve a guardar el punto de partida con el sentido nuevo; pasar a crédito de almacén lo quita. `GET /` trae `saldoInicial: {monto, fecha} | null` en cada método. Eliminar el método borra su punto de partida (no cuenta como uso). Desde gastos/ingresos personales ese movimiento no se edita, borra ni cambia de estado o método (409).
- Compras a cuotas personales y del hogar aceptan `cuotasPagadasAntes` (0–71, menor que `numeroCuotas`; también al editar, y recalcula): se crean solo las cuotas que faltan, con `numeroCuota` desde `cuotasPagadasAntes + 1` y la primera en `fechaPrimeraCuota` (la de la próxima cuota). Las pagadas antes no se registran: no tocan Disponible, consumo, saldo del hogar ni cuadres; el informe por método las cuenta como cobradas. En el hogar, si no había split en `fechaCompra`, una compra en curso se reparte con el split vigente.

### Catálogos personales — `/api/metodos-pago-personales` y `/api/categorias-personales` — requieren sesión activa
Un método de pago tiene `tipo` (`efectivo`, `debito`, `tarjeta_credito`, `credito_almacen`, `otro`); tarjeta de crédito guarda `diaCorte`, `diaPago`, `cupo` y opcionalmente `ultimos4` (validado: exactamente 4 dígitos — nunca el número completo, el código ni el vencimiento); crédito de almacén guarda `diaPago` y `cupo`. Los campos que no aplican al tipo se limpian.
- `GET /`, `POST /`, `PATCH /:id`, `DELETE /:id` — CRUD simple por usuario. `DELETE` falla con 409 si el método/categoría ya está referenciado por algún gasto, ingreso o concepto fijo. Una categoría tiene `aplicaA: string[]` (subconjunto de `gasto`/`ingreso`/`ahorro`) — el mismo catálogo de categorías se reusa entre los tres módulos en vez de tener uno por tipo.

### Ahorros personales (`/api/ahorros-personales`) — requieren sesión activa
- `GET /` — lista plana de metas (para el CRUD de configuración).
- `POST /` — `{ nombre, montoMetaTotal?, reglaTipo: "porcentaje"|"monto_fijo", reglaValor, baseCalculo?, modoTransaccion: "automatico"|"manual", categoriaId? }`. `reglaTipo`/`reglaValor` solo generan la sugerencia — nunca mueven plata por sí solos.
- `PATCH /:id`, `DELETE /:id` — igual patrón que los demás catálogos/configs; `DELETE` falla con 409 si la meta ya tiene aportes o pronósticos (desactívala con `PATCH { activo: false }`).
- `POST /:id/transacciones` — `{ monto, fecha? }` → aporte manual (`origen: manual`); solo tiene sentido para metas `modoTransaccion: manual` (las automáticas se debitan solas al evaluarse un período).
- `GET /resumen` — la vista de Panel personal: antes de responder, **evalúa perezosamente** el período actual (`evaluarPeriodoSiCorresponde`) por si ya cumple la condición y nadie lo disparó pagando un gasto obligatorio. Devuelve `totalAhorradoAcumulado` (todas las metas activas, histórico; con `?ciclo=-N`, al cierre de ese ciclo), `alertaSobregasto` (para el período actual ya evaluado; false en un ciclo pasado), por cada meta `cicloConsultado` (`montoSugerido` y `estado` si ese período se evaluó, y `montoAhorradoReal` aportado en él — con `?ciclo=-N` no salen las metas creadas después) y, sus últimos períodos evaluados con `montoSugerido`/`montoAhorradoReal`/`estado` (`amarillo`/`azul`/`verde`) — `montoAhorradoReal` se calcula sumando `AhorroTransaccion` dentro del rango en cada consulta, no se guarda como columna.

**Disparador de evaluación** (`src/utils/evaluacionAhorro.js#evaluarPeriodoSiCorresponde`): dado un `usuarioId` y una `fecha`, calcula el período (según `Usuario.frecuenciaCicloPersonal`) que la contiene; si ya fue evaluado, no hace nada (idempotente). Si no, revisa si **todos** los `GastoPersonal` con `esObligatorio: true` y `fecha` dentro de ese rango están `pagado` — si aún hay alguno `pendiente`, tampoco hace nada. Si se cumple, crea el snapshot `PeriodoAhorroEvaluado` (ingreso/obligatorios/no-obligatorios del período) y, por cada meta activa, su `AhorroPronostico` (`Base × reglaValor` o `reglaValor` fijo, según `baseCalculo`); si la meta es `modoTransaccion: automatico`, además crea de una vez su `AhorroTransaccion` por el monto sugerido. Se llama desde dos lugares: `gastosPersonales.service.js` (al crear o actualizar un gasto que quede `pagado` + `esObligatorio`) y `GET /api/ahorros-personales/resumen` (perezoso, para el período anterior y el actual — cubre el caso de "revisión periódica" que el documento describe sin asumir que existe un cron en esta app). **Un período en curso sin ningún obligatorio no se evalúa** ("todos pagados" se cumpliría desde el día 1 y quedaría guardado con el ingreso todavía en $0): en curso hace falta al menos un obligatorio y todos pagados; un período ya terminado se evalúa siempre que no le queden pendientes. Solo se aplican las metas creadas antes de que terminara el período, para no pronosticar ni debitar en un período pasado una meta que todavía no existía.

### Límites personales (`/api/limites-personales`) — requieren sesión activa
- `GET /` — lista plana de límites (para el CRUD de configuración).
- `POST /` — `{ nombre, tipoObjetivo: "categoria"|"obligatorios"|"no_obligatorios"|"todo_gasto", categoriaId?, reglaTipo: "porcentaje"|"monto_fijo", reglaValor }`. `categoriaId` es obligatorio si y solo si `tipoObjetivo: "categoria"` (400 en cualquier otra combinación).
- `PATCH /:id`, `DELETE /:id` — igual patrón que Ahorros; `DELETE` falla con 409 si el límite ya tiene evaluaciones de períodos pasados guardadas (desactívalo con `PATCH { activo: false }`).
- `GET /resumen?ciclo=0` — tarjetas de Panel personal: por cada límite activo, `actual` (período que contiene hoy, **siempre recalculado en vivo**, nunca se guarda) y `anterior` (el período previo, snapshoteado la primera vez que se consulta). Con un ciclo pasado, `actual` es el snapshot de ese período, y solo aparecen los límites creados antes de que terminara y que siguen activos o tienen evaluación guardada de ese período. Cada evaluación trae `limiteCalculado`, `montoGastado`, `disponibleRestante`, `estado` (`dentro`/`excedido`).

**Cálculo** (`src/utils/evaluacionLimite.js`): `ingresoPeriodo` = suma de `IngresoPersonal` en estado `recibido` dentro del rango (mismo criterio que Ahorros). `montoGastado` = suma de `GastoPersonal` en estado `pagado` dentro del rango, filtrado según `tipoObjetivo` (por `categoriaId`, por `esObligatorio: true/false`, o sin filtro para `todo_gasto`). `limiteCalculado` = `reglaTipo: "porcentaje"` → `round(reglaValor/100 × ingresoPeriodo)`; `"monto_fijo"` → `reglaValor` directo. `estado: "excedido"` si `montoGastado > limiteCalculado`. Cualquier período **pasado** (el anterior en la vista actual, o el ciclo consultado con `?ciclo=-N`, `obtenerEvaluacionPasada`) se busca primero en `LimiteEvaluadoPeriodo` (`@@unique([limiteId, periodoInicio])`) y solo se calcula y guarda si no existe, para que un cambio posterior de `reglaValor` no reescriba ese snapshot.

## Notas de diseño

- El esquema de Prisma solo incluye las tablas necesarias hasta la fase actual; el resto del modelo de datos se agrega incrementalmente en fases posteriores.
- **Cuadres abiertos (2026-11-24):** el motor de cortes por fechas nominales (frecuencia de corte del hogar, puntos de corte, atrasos, corte complementario) se reemplazó por cuadres sin fecha. El motivo: el hogar no cuadra cada quincena o mes, sino cuando lo necesita, y casi toda la complejidad del motor existía para tapar el desfase entre la fecha nominal y la real. Ahora una cuenta fija solo genera deuda cuando alguien la marca pagada, y un cuadre toma todo lo pagado hasta hoy. La migración `20261124120000_cuadres_abiertos` borró los datos de hogar existentes (cortes, cuentas, gastos variables y los gastos personales que generaron los cortes) — decisión de "hogar limpio" con el usuario.
- El split de porcentaje se modela como una fila por miembro (`SplitPorcentajeMiembro`), no como columnas fijas `usuario1`/`usuario2` — el modelo de datos soporta hogares de N personas, no solo parejas. Los repartos de gastos recurrentes/variables siguen el mismo patrón (`GastoRecurrenteInstanciaReparto`, `GastoVariableParejaReparto`).
- "Quién pagó" y "cómo se reparte" son conceptos separados: cada cuenta fija tiene un `responsable` (pagador por defecto al marcarla pagada, editable en cada pago); el reparto es siempre proporcional al split vigente en la fecha del gasto (o manual, en gastos variables).
- Todo acceso a datos que dependa del usuario autenticado se filtra a nivel de query por su `id`/`hogarId`, nunca solo en la capa de aplicación.
- Resolver el origen real (nombre/fecha/pagador/reparto) de un `CuadreItem` se hace por lote (`src/utils/cuadreItemOrigen.js#obtenerOrigenesDetalladosPorLote`): dos queries `findMany` con `id: { in: [...] }` (cuotas y gastos variables), sin importar cuántos ítems haya. Los cambios de estado de muchos orígenes también van en una `updateMany` por tipo.
- **Panel personal reestructurado (Fase 7):**
  - **Etapa 1:** la iteración anterior de esta fase tenía un motor de "cortes personales" (concepto + instancia + mini-corte de revisión, calcado del de pareja) — se eliminó por completo (schema, endpoints y UI) a favor de un modelo más simple: `GastoFijoConfig`/`IngresoFijoConfig` generan directamente filas reales en `GastoPersonal`/`IngresoPersonal` (`asegurarInstanciasFijas`, en `gastosPersonales.service.js`/`ingresosPersonales.service.js`), sin ninguna tabla intermedia ni evento de "cierre" — la fila generada YA ES el gasto/ingreso real, en estado `pagado`/`pendiente` según el modo configurado. Cada concepto fijo ancla su calendario en su propia `fechaInicio` (`src/utils/instanciasFijas.js#calcularFechasPendientes`), sin depender de puntos de corte compartidos como el hogar.
  - **Etapa 2:** se eliminó el módulo `dashboard` genérico que mezclaba resumen personal y de hogar — cada resumen ahora vive en su propio dominio (`obtenerResumenHogar`, hoy en `cuadres.service.js`; `resumenPersonal` como módulo nuevo). El ciclo personal (`cicloPersonal.js`) es deliberadamente más simple que el corte de hogar: sin puntos configurables, cada período se calcula puramente por calendario a partir de una sola frecuencia (`Usuario.frecuenciaCicloPersonal`). `disponible` es histórico a propósito (no por período) — es la métrica de "cuánto tengo ahora"; `neto` sí es por período, para poder compararlo contra el ciclo anterior.
  - **Etapa 3 — Ahorros:** `PeriodoAhorroEvaluado` se crea **una sola vez por período** (`@@unique([usuarioId, periodoInicio])`) — es lo que evita disparar la misma alerta/débito automático repetidamente para un período ya evaluado; la evaluación en sí es idempotente y se puede llamar de más sin efecto. `AhorroPronostico` guarda `montoSugerido` pero deliberadamente **no** guarda `montoAhorradoReal` ni el color del semáforo (a diferencia de como los describe `Modulo_Panel_Personal_Ajustes.md`) — se calculan en vivo sumando `AhorroTransaccion` dentro del rango del período cada vez que se consulta el resumen, para no tener que mantener un campo cacheado sincronizado a mano cada vez que entra un aporte nuevo. Tampoco hay cron en esta app para la "revisión periódica programada" que menciona el documento — se sustituye evaluando también de forma perezosa cada vez que se consulta `GET /api/ahorros-personales/resumen`, mismo patrón que `asegurarInstanciasFijas`.
  - **Etapa 4 — Límites:** igual patrón dual que Ahorros (vivo para el actual, snapshot para el pasado) pero sin condición de disparo — a diferencia de `PeriodoAhorroEvaluado` (que solo se crea cuando todos los obligatorios ya están pagados), el período **actual** de un límite se recalcula en cada consulta sin excepción, porque tiene sentido ver el límite moverse en vivo mientras uno gasta. Solo el período **anterior** se snapshotea (una vez), porque ese sí ya es historia cerrada. `reglaTipo` reusa el enum `ReglaAhorroTipo` (mismo set de valores porcentaje/monto_fijo) en vez de duplicarlo.
  - **Etapa 5 — Integración con el hogar:** ver la nota "Integración con el panel personal" en la sección de Cuadres más arriba — la decisión de diseño central fue usar el **reparto** de cada miembro (lo que gastó de verdad) y no el `balance` neto (que es para saldar cuentas entre quien pagó primero y quien no) como monto del `GastoPersonal` generado.
  - **Estabilización post-Etapa 5:**
    - **"Hoy" en hora de Colombia** (`src/utils/fechas.js#hoyUTC`, `APP_TZ` para cambiarla): las fechas de calendario se guardan como medianoche UTC, pero "hoy" se calculaba con el reloj UTC — desde las 7pm ya era mañana, y se generaban fijos/períodos un día antes.
    - **Carrera al cargar el panel:** Resumen, Límites y Ahorros corrían en paralelo con el listado de gastos, antes de que se generaran los fijos del período, y Límites/Ahorros guardaban ese snapshot incompleto. Ahora cada cálculo llama `asegurarInstanciasFijasPersonales` (`src/utils/instanciasFijasPersonales.js`) antes de leer; la generación usa `skipDuplicates` y los snapshots toleran el P2002 de una consulta paralela. Además Ahorros no evalúa un período mientras le quede una ocurrencia fija obligatoria todavía por generar (fecha posterior a hoy dentro del período), y el débito automático de un período ya terminado cae en su último día. `scripts/recalcularHistorialesPersonales.js` limpia y recalcula lo que quedó mal guardado.
    - **Fecha del gasto personal del hogar:** con los cuadres abiertos, un gasto por mes de los ítems (último día del mes, o el día del cuadre si es el mes en curso) — ver la sección de Cuadres.
  - Ver `Modulo_Panel_Personal_Ajustes.md` para el diseño completo de la etapa siguiente (navegación histórica por ciclo).
